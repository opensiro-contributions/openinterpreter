## Why this might matter
An Open Interpreter operator could hypothetically run **two MultiAgentV2 child tasks while only one V2 execution slot is available** (`max_threads=1`). Current `list_agents`, message/follow-up controls and static limiter expose statuses and enforce a limit, but do not provide an authorized *which waiting child gets the next turn* policy. An optional root-authorized, developer-composed **V2 turn-admission arbiter** could choose a priority, safely admit the next child and confirm the later outcome before choosing again. This is architectural research, **not** an observed bug, a proven utility gain, or a request to maintainers to adopt VSM.

## Proposed capability, in ordinary language
With MultiAgentV2 opted in, the user could **configure a developer-composed policy to select which child gets the next execution turn** when current tasks contend for the root session's fixed execution capacity. The actor observes existing V2 statuses plus a **proposed** revisioned queue of pending follow-up intentions, chooses a permitted child or defers, and only then submits through the existing native delivery path subject to an **additional proposed checked admission/permit bridge**. Later status and real terminal feedback must influence its next decision; a successful message submission alone is insufficient. This does **not** entail automatic direct reassignments or cross-session resource governance.

The missing native implementation is a root-authorized policy registration, small revisioned pending-follow-up intent, an **atomic V2 turn-admission decision** linked to `agent/control/execution.rs`, and credible status/terminal outcome correlation. Native `agent/control/delivery.rs` provides target resolution and a submission receipt; `completion.rs` returns child outcomes only on a **best-effort** basis. All additional rights/effect/feedback guarantees are proposed rather than shipped. No root policy grants, Guardian bypass or new general scheduler.

## Track A versus Track B
Track A has first-party [multi-agent status](https://github.com/openinterpreter/openinterpreter/blob/7a5509e307cc56d66f5c7413955bb387ab895815/codex-rs/core/src/tools/handlers/multi_agents_v2/list_agents.rs), [agent-control](https://github.com/openinterpreter/openinterpreter/blob/7a5509e307cc56d66f5c7413955bb387ab895815/codex-rs/core/src/agent/control.rs), [child completion return](https://github.com/openinterpreter/openinterpreter/blob/7a5509e307cc56d66f5c7413955bb387ab895815/codex-rs/core/src/agent/control/completion.rs), [fixed child limits](https://github.com/openinterpreter/openinterpreter/blob/7a5509e307cc56d66f5c7413955bb387ab895815/codex-rs/core/src/agent/control/execution.rs), and optional Guardian. [Original PR #1973](https://github.com/openinterpreter/openinterpreter/pull/1973) proposes Goal CAS but is **open/unmerged**; [PR #1981](https://github.com/openinterpreter/openinterpreter/pull/1981) is also **open/unmerged**. [Issues #1926](https://github.com/openinterpreter/openinterpreter/issues/1926) and [#1927](https://github.com/openinterpreter/openinterpreter/issues/1927) address different task-level failures.

Track B proposes a **MultiAgentV2-specific next-turn selection** around `LocalAgentControl`, V2 `followup_task`/native `TriggerTurn`, `execution_guard` and recorded child results, not a copy of a generic supervisor or another message board. The existing board cannot activate idle agents, and delivery receipts are not terminal task evidence. A matched two-child V2 baseline, atomic-capacity test, revoked-root denial and missing-feedback behavior must be checked in future code before claiming an implementation.

## Native-specific review under Upstream v0.18.1 (2026-11-20)

This is a **review of the same previous Wave 4 case**, not a new independent first-pass or an Index regrade. Under the [v0.18.1 native-specific recommendation](https://github.com/opensiro/upstream/commit/14973244a474cc643c01ce04d70913f51c714b74), the earlier generalized "shared-commitment supervisor" phrasing was **too broad**: no first-party atomic reassign/acknowledge primitive or guaranteed S3 feedback loop was found. The revised proposal is **one opt-in MultiAgentV2 root-session next-turn admission decision**, with no other controller or reporting feature.

The author would reuse [status listing](https://github.com/openinterpreter/openinterpreter/blob/7a5509e307cc56d66f5c7413955bb387ab895815/codex-rs/core/src/tools/handlers/multi_agents_v2/list_agents.rs), [native target resolution and follow-up delivery](https://github.com/openinterpreter/openinterpreter/blob/7a5509e307cc56d66f5c7413955bb387ab895815/codex-rs/core/src/agent/control/delivery.rs), [V2 capacity permit](https://github.com/openinterpreter/openinterpreter/blob/7a5509e307cc56d66f5c7413955bb387ab895815/codex-rs/core/src/agent/control/execution.rs) and [best-effort completion](https://github.com/openinterpreter/openinterpreter/blob/7a5509e307cc56d66f5c7413955bb387ab895815/codex-rs/core/src/agent/control/completion.rs); the new priority/permit/feedback coupling must still be constructed and tested. If it cannot act lawfully or verify the subsequent effect, the proposal must be reconsidered; a plan-only `GO / NEEDS_EVIDENCE` is **not** a working feature or endorsement. No additional scores or gates, no product edits, no external publication, no native tests.
